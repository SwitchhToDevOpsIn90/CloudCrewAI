# Playbook: Deploying from GitHub Actions to EKS with No Stored AWS Keys

## WHY

A pipeline that deploys needs AWS access. The usual shortcut is an access key in GitHub Secrets: it works forever, for anyone who finds it, and it is rarely rotated. OpenID Connect (OIDC) replaces it: GitHub vouches for which workflow is running, AWS issues credentials that last about an hour, and the role they belong to can be limited to one repository, one branch or environment, and one namespace. Nothing long-lived is stored. The aim is that a merge to main deploys with no manual steps, the deploying identity can do very little, and everything created for the lesson is removed with proof.

## WHAT This Playbook Delivers

An OIDC identity provider and a deploy role in AWS, a deploy job that waits behind an approval, pushes the exact image that passed CI to ECR, applies manifests pinned to its digest, verifies the rollout and smoke-tests it, and proves its own boundaries. Plus a cluster built for the session and torn down with a sweep that proves nothing billable is left.

## Prerequisites

The pipeline from github-actions-secure-ci-pipeline.md, with one required gate job. A cost ceiling written down before anything is created: the OIDC provider and role are free, but the EKS control plane bills about $0.10 an hour plus nodes and a NAT gateway, so decide how many hours, use small nodes (t3.small), and confirm the credit balance first. Creating the cluster, roles and policies needs the operator's approval; cluster work follows eks-cluster-setup.md. Mask the account ID everywhere outside the terminal.

## Steps

1. Pre-flight, read-only: confirm which account and identity you are using (`aws sts get-caller-identity`), whether a GitHub OIDC provider already exists (`aws iam list-open-id-connect-providers`), and that no EKS cluster is left over.

2. Register the identity provider in IAM: provider URL `https://token.actions.githubusercontent.com`, audience `sts.amazonaws.com`. One per account is enough.

3. Create the deploy role with a trust policy that checks the `sub` claim. That condition decides which GitHub workflows can assume the role, so make it exact: this repository and the `production` environment (`repo:<owner>/<repo>:environment:production`), never a wildcard on the repository or on all branches. Also check `aud`. Give the role only the permissions the deploy needs: push to one ECR repository and describe the cluster. Keep the trust and permission policy files, with the account ID as a placeholder, in the repository's notes so the setup can be rebuilt.

4. Keep the account ID out of the code and out of the logs. Store the role ARN and the ECR repository address as environment secrets (on the `production` environment), not as variables: variables are never masked, so a public repository's logs and step headers print them in full. The session first used variables and the account ID appeared in the logs of four public runs. Keep the role's trust and permission policies and the cluster file in the repository with a `${AWS_ACCOUNT_ID}` placeholder (render with `envsubst`), so the setup can be rebuilt from Git without publishing the ID.

5. Give the deploy job `permissions: id-token: write` and `contents: read`, and nothing else. Without `id-token: write` the run cannot request a token at all. Put the job in a GitHub environment named `production` with a required reviewer, so every deploy waits for a human. Use `concurrency` with `cancel-in-progress: false` so two deploys never overlap, and run it only on pushes to main after the gate job passes.

6. Assume the role with `aws-actions/configure-aws-credentials`, pinned to a commit SHA, and set `mask-aws-account-id: true` explicitly; do not assume the default. Print `aws sts get-caller-identity` once to show a short-lived role session. Then prove the masking in the public run log (`***` where the ID would be, and `grep -c <id>` on the log returning 0), because logs of public repositories are public. If an ID has already been printed, the old logs can be deleted through the API; the ID stays in any commit that contained it.

7. Push the exact image that passed smoke and scan: load the tar that CI built, tag it with the commit SHA, push, and read back the digest. Never rebuild at deploy time.

8. Deploy by digest: substitute the digest reference into the manifest, `kubectl apply`, then `kubectl rollout status` with a timeout. Use a rolling update with `maxUnavailable: 0`, a readiness probe, resource requests and limits, a non-root user, `allowPrivilegeEscalation: false` and dropped capabilities.

9. Smoke-test inside the cluster and print the running image reference to show that it is the digest.

10. Box the deploy identity into its namespace and prove it in the pipeline: grant access through an EKS access entry with a namespaced policy (edit rights in one namespace only), then fail the job unless `kubectl auth can-i` says yes for creating deployments in that namespace and no for creating deployments in `kube-system`, reading secrets there, and creating namespaces.

11. Prove the identity boundary from outside: a pull request branch, or any workflow that is not `main` plus the `production` environment, must be refused when it tries to assume the role (the expected error is that the web identity token cannot be used, not a permissions error later). Prove that the developer's everyday key alone cannot reach the cluster either; administrator rights come only from a temporary role session, and that role is deleted at the end.

12. Tear down in the same sitting, in order: delete the cluster stack and wait for it to finish (if the delete says an update is in progress, wait and retry), then sweep with four checks that must each return an empty list: clusters, NAT gateways in available or pending state, VPCs tagged for the cluster, and stacks for the cluster that are not DELETE_COMPLETE. Delete the temporary admin role and remove the local profile that pointed to it. An access error for the old role proves access is gone, not that the role is gone; check the role list or the console count.

13. Decide what stays and say so: the OIDC provider, the deploy role and the ECR repository are small and free to keep, but a deploy job that still runs on every merge will fail once the cluster is gone. Switch it off with a repository-level variable in the job condition (for example `&& vars.DEPLOY_ENABLED == 'true'`; a job's `if` cannot read environment-level variables), set to false until a new cluster exists. Proof: the next run on main shows every CI job successful and the deploy job skipped, with no approval prompt.

## Guardrail Check

Never store long-lived AWS keys in GitHub for deployment. Never write a trust policy that does not pin the repository and the environment or branch. Never give the deploy role administrator rights, IAM changes, or access outside one namespace. Never deploy by a mutable tag; deploy by digest. Never create an EKS cluster without a written cost ceiling and a teardown in the same sitting. Never commit the account ID, a role ARN containing it, or a kubeconfig; use placeholders and environment secrets, never plain variables for anything containing the ID, and scan before committing (`git grep` for the real ID must print nothing). Never skip the approval gate on a production environment. Never claim cleanup from an access-denied error alone. Creating IAM roles, providers and clusters needs the operator's approval.

Found afterwards and fixed in pull request 36 (eb5a68c, seen in the merge output and a main run where all seven CI jobs succeeded and deploy was skipped): `cluster.yaml` had been merged with the full account ID in a role ARN in a public repository, and the role ARN and ECR address were plain variables that the public run logs printed. The fix moved both to environment secrets, set `mask-aws-account-id: true`, put a placeholder in `cluster.yaml`, added the trust and permission policies to the repository with placeholders, and added the `DEPLOY_ENABLED` switch (false). The scan of the working tree and `git grep` for the real ID both came back empty. Still open: the old commits and the logs of four older public runs still contain the ID (history rewrite planned for Session 90, log deletion optional); the masking has not yet been proven on a run with the switch on; the role deletion is reported without a listing; a Dependabot update to the credentials action (pull request 35) was waiting for review. Other gaps: no automatic rollback if `rollout status` fails (old pods keep serving because of `maxUnavailable: 0`, but nothing reverts); the smoke test uses a fixed sleep; re-running a deploy for the same commit fails if ECR tags are immutable. Open follow-ups from the lab: gunicorn for graceful shutdown, and change-cause on rollout revisions.
