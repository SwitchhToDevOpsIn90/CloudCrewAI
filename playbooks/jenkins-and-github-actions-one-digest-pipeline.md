# Playbook: Two CI Tools, One Image Digest, One Deploy Path

## WHY

Real teams rarely run one CI tool. One team builds in Jenkins, another in GitHub Actions, and a third tool scans what runs in production. The danger is not that the tools disagree about syntax. It is that they build two different images of the "same" commit, deploy through two different paths with two sets of cloud keys, or trust each other's word that "the scan passed". Integration means agreeing on who builds, who deploys and what is handed over. The hand-over is the image digest and nothing else, the deployer checks it again instead of trusting the caller, and there is exactly one deploy path with one approval gate and one identity check.

A second problem comes with it. A Jenkins server on a laptop or a VM cannot use OpenID Connect to reach AWS, so it needs a cloud identity and a GitHub token. Every such credential must be as small as possible, must expire by itself, and must be removed with proof at the end of the sitting.

## WHAT This Playbook Delivers

One shared deploy action used by two entry points (the CI workflow and a manually or remotely started "deploy this digest" workflow), a Jenkins pipeline that tests, builds for the right CPU architecture, scans, pushes to the registry as an assumed role and optionally asks GitHub Actions to deploy the digest it pushed, a scheduled Jenkins job that scans whatever production actually runs through a read-only role, and a cleanup that removes every temporary credential with a check for each. A GitLab CI version of the same pipeline can be written for comparison, clearly labelled as never run.

## Prerequisites

The deploy path from github-actions-oidc-deploy-to-eks.md (OIDC role pinned to one repository and the `production` environment, approval gate, digest-only deploys, namespace-boxed identity) and the Jenkins and ECR work from jenkins-docker-build-and-ecr-push.md. A cost ceiling written down before any cluster is created; the cluster comes up only for the deploy demonstrations and is removed in the same sitting (eks-cluster-setup.md). The operator approves creating every user, role, token and the cluster. Mask the account ID in every file, screenshot and log that leaves the terminal. A repository variable (not an environment variable) as the deploy switch, so the deploy job can be skipped while no cluster exists.

## Steps

1. Pre-flight, read-only: confirm the account and identity (`aws sts get-caller-identity`), the build host's CPU architecture, the cluster nodes' architecture, and that no cluster is left over. A Mac builds arm64 and the nodes are amd64; the mismatch has to be handled in step 5, not discovered at deploy time.

2. Write down who does what before writing any pipeline. A workable split: Jenkins builds, tests, scans and pushes; GitHub Actions deploys; a scheduled Jenkins job scans what production runs. The hand-over between builder and deployer is the digest (`sha256:` plus 64 hex characters), never a tag. Two builds of the same commit on different tools produced different digests (a85ed68d and f3c87006 in the lab), so a tag cannot name "the image that was tested".

3. Make one deploy path. Put the deploy steps in a composite action that both entry points call. The action refuses any image not pinned by digest, applies the manifest, rolls out with a timeout and undoes the rollout if it never becomes healthy, smoke-tests with retries instead of a fixed sleep, records the reason for the revision (change-cause), and finishes with the namespace guardrail (`kubectl auth can-i` must answer yes, no, no, no). Two ways to start a deploy, one way to deploy.

4. Make the second entry point distrust its caller. The "deploy this digest" workflow validates its inputs against strict patterns, checks that the digest exists in the registry, pulls it and fails unless the architecture matches the nodes, and scans it again with the scanner before the shared action runs. Keep the same environment, approval gate, role and concurrency group as the CI deploy. It runs only on main and only while the repository-level deploy switch is true.

5. Build the Jenkins pipeline in stages that each fail loudly: hashed dependency install and tests (`pip --require-hashes` applies to the whole command, so install the hashed and unhashed requirement files in separate commands), build with `--platform linux/amd64` and assert the architecture of the result, smoke test (emulated), scan with a pinned scanner version failing on fixable HIGH and CRITICAL findings, then push.

6. Push as an assumed role, not as the long-lived user. The Jenkins credential belongs to an IAM user that can do nothing except assume one push role limited to one repository, with a 15-minute session. Put the time limit in the role's trust policy (`DateLessThan` on `aws:CurrentTime`), because the limit then holds even if someone forgets cleanup. Wrap the credential steps in `set +x`: Jenkins masks stored credentials, not the temporary keys returned by assume-role. Use a throwaway Docker config directory and read the digest back from the registry after the push.

7. Add the optional hand-off. Jenkins starts the deploy workflow through the `workflow_dispatch` API with a fine-grained GitHub token limited to one repository and to starting workflows, expiring in 7 days. Prove it cannot do more: an attempt to write code with that token must return 403. The deploy still waits for the human approval in GitHub; Jenkins asks, a person decides. Check the deployed image: the running pod's image reference must be the digest Jenkins pushed, and the rollout history should show which tool started each revision.

8. Add the production scanner. A scheduled Jenkins job resolves the registry tag `production` to a digest, pulls that digest and scans it. A scheduled scan matters because new vulnerabilities appear against an image that did not change. Give it its own read-only role (login, then read and describe on one repository), never the push role. Move the `production` tag as the last step of the deploy action, after rollout, smoke test and guardrail passed, so the tag means "this digest is what is running". Know the limits before relying on it: moving a tag fails once the registry's tag immutability is on (exempt only `production` with an immutability exclusion, or write the digest to a parameter store instead), and the tag step is only proven after it has run in a live deploy.

9. Expect the first run of a new Jenkins pipeline to fail on parameters. Jenkins learns declared parameters and the cron schedule only after the first run, so the first build arrives with an empty parameter and the cloud call is rejected (a parameter-validation error, not a missing-tag error). Run it once to register, then run the real build. Do not mistake this for a pipeline bug, and do not leave a default that depends on the tag existing.

10. Run each path and keep the evidence: the build that failed and why, the build that passed, the run that deployed. Save the raw logs, mask every 12-digit number with `sed`, then count leftover 12-digit numbers and token-like strings (`github_pat_`, `ghp_`, `AKIA`, `ASIA`) in the saved files. Both counts must be 0 before any file is shared.

11. Tear down the cluster in the same sitting using the sweep from github-actions-oidc-deploy-to-eks.md, and switch the deploy switch off. Proof: the next run on main shows deploy skipped, with no approval prompt.

12. Remove every temporary credential, and check each one by its own kind, not by one catch-all. Jenkins: delete the stored credentials, delete the login file used by the command-line client, and read every user's token list from the Jenkins home on disk (`<tokenList/>` must be empty for every user). AWS: delete the temporary user and its access key, delete the push and read roles, and check by name in the console (search `jenkins`, the session name and the cluster tool's prefix, each must show 0 matches); a total count is weak evidence because it needs the earlier count to be right. GitHub: no fine-grained tokens, no classic tokens (classic tokens with the `repo` scope and no expiry grant access to every repository). Local machine: check the git credential helper. A `store` helper keeps the login in a plain-text file in the home folder; point git at the CLI login (`gh auth setup-git`), delete the file, erase the Keychain entry, then prove pushing still works with a push dry run (a read of a public repository proves nothing, because it needs no login).

13. Say what stays and what stopped working. A scheduled job whose credentials were deleted cannot run, so disable it and write that in the README instead of leaving a weekly failure. A permanent identity for Jenkins without stored keys is still open work.

## Guardrail Check

Never hand a tag between CI tools; hand a digest, and let the deployer check it again (exists, right architecture, scanned). Never keep two deploy paths with two sets of cloud credentials; keep one action with one gate. Never give a CI tool a long-lived cloud user that can do more than assume one scoped role, and never leave a temporary credential without an expiry built into its trust policy or token. A hand-off token must be limited to one repository and unable to write code, and that must be shown by a refused write. Never create users, roles, tokens or clusters without the operator's approval. Never share saved logs before masking and counting leftover account IDs and token-like strings. Never claim cleanup from an access-denied error or from a total count; check each credential by its own listing or search. Never commit the account ID or a role ARN containing it; use a placeholder and `envsubst`. Never rely on a tag that moves unless immutability has been checked. Tear down the cluster in the same sitting.
