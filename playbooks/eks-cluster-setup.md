# Playbook: AWS EKS Cluster Setup, Operations, and Real-Cost Teardown Verification

## WHY

EKS carries a fundamentally different cost and risk profile than most resources covered elsewhere in this framework — a control plane fee billed continuously while it exists, worker nodes on top of that, and no free tier. eksctl also creates multiple AWS resource types simultaneously (VPC, IAM roles, CloudFormation stack, the cluster itself), meaning a failed or incomplete attempt can leave several different kinds of orphaned resources behind, not just one. This genuinely warrants more rigorous safety discipline than a simpler single-resource provisioning task.

## WHAT This Playbook Delivers

A working EKS cluster provisioned safely within an explicit cost boundary, genuine operational fluency (rolling updates, rollback, interactive shell access) proven against real infrastructure rather than just a local cluster, and a rigorous, multi-resource-type teardown verification proving nothing was left running, repeated consistently across every session touching real EKS infrastructure.

## Prerequisites

eksctl installed. Real, current EKS pricing confirmed (per the cloud cost optimization playbook's escalation-trap awareness) before starting. An explicit hard cost ceiling and session-bound completion rule established before touching anything, per the bounded demo provisioning playbook.

## Steps

1. Verify actual IAM permissions before assuming a policy is sufficient. eksctl requires far broader permissions than the EKS API alone — it creates a VPC, multiple IAM roles, and a CloudFormation stack in the same operation. A policy scoped only to eks:* actions (mistaking a service-role policy like AmazonEKSClusterPolicy for what a human or CLI caller needs) will fail partway through, not upfront — confirm the caller's actual permissions cover IAM role creation and CloudFormation, not only EKS-specific actions.

2. Use a genuinely Free Tier eligible instance type for worker nodes, and verify this specifically rather than assuming any small-sounding instance type qualifies. t3.medium is a common default in tutorials and examples but is not Free Tier eligible; t3.small and t3.micro are. Using a non-eligible instance type causes node group creation to fail during CREATE_IN_PROGRESS, confirmed via a real AsgInstanceLaunchFailures error stating the instance type is not eligible for Free Tier — this can consume a significant, unproductive time window before failing.

3. When a permission-related failure occurs, fix the specific denied action rather than broadening scope generally, and expect this may reveal a second, deeper permission gap once the first is resolved — this "peel one layer, find another" pattern is a common, expected part of getting a genuinely correctly-scoped policy right, not a sign something is fundamentally wrong.

4. Be aware that a CloudFormation stack created by eksctl may have termination protection enabled by default, which can cause a failed stack to become stuck in a ROLLBACK_FAILED state that ordinary deletion cannot resolve — this requires explicitly disabling termination protection on that specific stack before deletion will succeed.

5. When a resource creation step fails without a clear, captured error message, document this honestly as unresolved rather than guessing at an explanation — but also capture the stack's actual event log before deleting the failed stack wherever possible, since deleting a failed stack before capturing its specific error events forecloses the chance to confirm root cause later, even when a strong circumstantial connection to a later, similar failure eventually emerges.

6. Once a cluster is genuinely running, verify real operational commands work against it, not only that the cluster exists: a rolling update (kubectl set image or kubectl apply with a new image tag), a deliberate rollback test (intentionally deploy a genuinely non-existent image tag to trigger ImagePullBackOff, confirm existing healthy pods remain untouched and serving traffic throughout, then kubectl rollout undo to recover), and kubectl exec for direct interactive shell access to a running pod — confirming both security posture (which user the container actually runs as) and configuration (that injected ConfigMap or Secret values are genuinely present) in the same check.

7. After any attempt — successful, failed, or abandoned — verify teardown across every distinct resource type eksctl may have touched, not only the cluster itself: the EKS cluster (aws eks list-clusters), any CloudFormation stacks in any failed or rolled-back state as well as completed ones, the VPC (confirming only the original default VPC remains), EC2 instances (confirming no worker nodes remain running, noting a terminated instance may show briefly in the console as expected temporary retention rather than a live billing resource), and IAM roles (searching specifically for role or policy names matching the tool or cluster name used) — including reverting any temporary IAM policies attached to a CLI user specifically for this work, restoring least-privilege scope afterward.

8. When confirming actual cost impact, cross-check at least two independent sources rather than trusting one figure — Cost Explorer's same-day data can lag and show an artificially low or zero figure for genuinely real recent usage, while cost anomaly detection, the billing summary page, or the account's own "does not get charged" free-plan confirmation may reflect a more current, accurate picture. State explicitly which figure is being trusted and why.

## Guardrail Check

Never assume a service-role policy (one meant to be attached to a resource the service itself assumes) is sufficient for a human or CLI caller's own permissions — these are genuinely different purposes even when named similarly. Never delete a stuck CloudFormation stack without first checking for and addressing termination protection specifically. Never delete a failed CloudFormation stack without first attempting to capture its actual event log, if root cause has not yet been identified. Never consider teardown complete after checking only the primary resource type (the cluster itself) when the provisioning tool is known to create multiple resource types — verify each type independently, every time real EKS infrastructure is involved, not only on the first attempt. Never present two disagreeing cost figures without explicitly stating which is trusted and the reasoning why. Never claim a root cause is independently confirmed for a specific historical failure when the actual evidence only directly confirms it for a separate, later attempt — state the distinction between confirmed and strongly-inferred explicitly.

## Reference Implementation

See github.com/SwitchhToDevOpsIn90/devops-journey, Session 34 — three real, distinct EKS provisioning attempts. Attempt one failed on eks:DescribeClusterVersions due to an incorrectly-scoped service-role policy being used for a CLI caller. Attempt two, after that fix, failed on a deeper iam:CreateRole permission gap. Attempt three succeeded through control plane and addon creation, then failed after approximately 35 minutes at the node group stage; the failed stack was deleted before its specific error events could be captured, leaving the precise cause of that particular attempt honestly undetermined at the time. All five resource types were independently reverified clean, with cost impact cross-checked between a same-day Cost Explorer reading showing $0.00 (attributed to genuine reporting lag) and a cost anomaly detection figure of $0.33, explicitly treated as the more trustworthy number given known Cost Explorer lag documented since Session 18.

See Session 35 for both the resolution and the continued discipline. A fresh cluster succeeded on the first attempt using t3.small (Free Tier eligible) and the full correct IAM permission set attached upfront. During this session's process, a separate fresh t3.medium attempt was deliberately made and directly confirmed, via a captured AsgInstanceLaunchFailures error, that t3.medium is not Free Tier eligible — the same instance type, failure stage, region, and account as Session 34's Attempt 3, providing strong circumstantial support that this was the same root cause, honestly documented as strongly inferred rather than independently proven for that specific historical attempt, since Attempt 3's own stack events were never captured. Real operational commands were proven against this cluster: a rolling update, a deliberate rollback test (a genuinely non-existent image tag triggering ImagePullBackOff while two existing healthy pods remained untouched throughout), and kubectl exec confirming both the Session 26 non-root user fix and a real ConfigMap value simultaneously inside a live pod on real EKS infrastructure. This session also marked the fourth genuinely distinct context in which the arm64/amd64 architecture mismatch first discovered in Session 23 recurred (Session 23's EC2 build, Session 29's review, Session 31's Minikube, and this session's real EKS node), reinforcing it as one of the most consistently transferable lessons across this framework. Full teardown was again independently reverified across all five resource types, including reverting temporary IAM policy grants back to least-privilege scope, with a final confirmed $0.00 real charge.
