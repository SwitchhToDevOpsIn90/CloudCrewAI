# Second /crew-sprint test: 2026-11-07

Task: on local Minikube, run Postgres 16 as a StatefulSet on a 1Gi PVC and dockerapp:1.0 as a 2-replica Deployment with a Service. Prove that data survives deletion of the Postgres pod, then tear down with proof. Cost $0, every command pinned to `--context minikube`. Verification by a separate agent. Deliverables are in ~/crew-sprint-2.

## What worked (the sprint-1 fixes held)
- **Dedicated namespace.** `crew-sprint-2` was listed in `.crew/owned.txt`. The hook allowed deleting exactly that namespace without approval. This is the first live proof that the hook behaves as designed.
- **Context pinning.** Every kubectl command was pinned. The EKS context on the machine was never used.
- **Separate verifier.** A separate agent did the verification in two passes: deployed state, then teardown. It received only the request files and read access.
- **Persistence proven.** Rows were written, then `postgres-0` was deleted. The pod UID changed and the PV stayed the same, and the rows were read back. The verifier corroborated this independently from API-server events, row timestamps and the heap file mtime.
- **Teardown sweep.** It ran twice and caught a leftover the playbook did not predict: an empty hostpath directory on the node.

## What the verifier caught (producer errors)
1. The ledger's "Verified by" cells were pre-filled with a report that did not exist yet.
2. A condensed copy of report 1 was labelled "verbatim".
3. "No AWS resources" was written in the ledger as fact. It cannot be observed under the no-AWS rule, so it is now labelled inferred.

## Findings about the system
- NetworkPolicy is not enforced on Minikube's default bridge CNI.
- The DockerApp image still has to run as root, because its packages are in /root/.local.

## Tooling
- **Subagent writes blocked.** The harness blocks file writes from subagents, so the producer has to save the verifier's report.
- **Hook false positive.** The hook blocked file-editing heredocs that contained namespace-delete text. They were edited with the Edit/Write tools instead; the hook was not bypassed for any real deletion.

## Still unproven
- The "$0 / no AWS" claim, by design: it is inferred, not observed.
- Survival across a node restart was not tested.
- The edits from this retro (kubernetes-persistent-storage.md, independent-verifier.md, hooks/README.md) are uncommitted, for human review with `git diff`.

## Follow-ups after review
- Hook false positive fixed: heredoc bodies that are only data are no longer checked (a heredoc fed to bash or another interpreter still is), and `kubectl --context X delete namespace <owned>` is accepted. Hook tests are now 29/29.
- The agent noted deleted pods in `default` stopping at 10:04 to 10:06Z, "before the sprint started", and attributed them to the operator's earlier work. Those times match the first sprint (about 13:00 to 13:08 local, UTC+3), so they were most likely sprint 1's own teardown. Inferred from timing, not proven.
- The verifier probe pod (NetworkPolicy test) appears to have been cleaned up (inferred: both teardown sweeps came back clean).

## First live run of tools/teardown-check.sh (same day, operator's Mac)
The CLI user had no read permissions (revoked after the earlier EKS sessions), so all ten checks returned AccessDenied. That correctly shows access is gone, but the old script then ended with "empty output means none found", which would read as a pass. Fixed: each check now reports NONE FOUND, FOUND or UNVERIFIED, account IDs are masked in output, and the exit code is 0, 1 or 2 (2 = unverified, never a pass). Tested with a fake `aws` command (tools/test_teardown_check.sh). The real AWS account state is still unverified: it needs the console (EC2 Volumes and Snapshots, EKS, Billing) or an operator-approved read-only role.
